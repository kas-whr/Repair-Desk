## 2. Источники данных

В Grafana используется datasource **VictoriaMetrics**, тип **Prometheus**, UID `victoriametrics`, URL внутри кластера:

```text
http://vm-single-victoria-metrics-single-server:8428
```

Источник добавляется автоматически из `k8s/monitoring/grafana/datasource.yaml`. Grafana получает данные через Prometheus-совместимый API VictoriaMetrics; напрямую к PostgreSQL она не подключается.

VictoriaMetrics собирает метрики с подов, аннотированных `prometheus.io/scrape: "true"`, с интервалом 15 секунд:

- API `/metrics`, порт 9090: HTTP-запросы, бизнес-метрики, Go/process metrics.
- Prober `/metrics`, порт 9090: успешность и длительность синтетического сценария.
- PostgreSQL Exporter, порт 9187: состояние БД и статистика транзакций, строк и подключений. Exporter работает вторым контейнером в поде PostgreSQL.

## 3. Дашборд приложения

Дашборд **Repair Desk — обзор и SLA**, UID `repairdesk-overview`, содержит 14 панелей. Исходный JSON: [`application.json`](../k8s/monitoring/grafana/application.json). Окончательный экспорт демонстрируемого дашборда: [application.json](application.json) — добавить файл после экспорта из Grafana.

### Верхнеуровневые метрики

- **Доступные API targets:** `sum(up{namespace="repair-desk",app="api"})`. Показывает число доступных для сбора метрик экземпляров API; ожидается 2 при двух готовых репликах. Доступность пользовательского сценария оценивается отдельно пробером.
- **Последний результат пробера:** `repairdesk_probe_success`, где 1 — успешная проверка, 0 — ошибка.
- **RPS по HTTP-статусам:** `rate(repairdesk_http_request_duration_seconds_count[…])` с суммированием по `status`. Показывает трафик и изменение кодов ответа.
- **Доля ошибок 5xx:** отношение частоты серверных ошибок к частоте всех запросов API.
- **Задержка API p95:** `histogram_quantile(0.95, …repairdesk_http_request_duration_seconds_bucket…)`. Показывает задержку, ниже которой укладывается примерно 95% запросов.
- **Доля запросов ≤250 мс:** отношение bucket `le="0.25"` ко всем запросам; порог внутреннего SLO — 99%.

В HTTP-панелях выбраны маршруты `/api/*`; служебные `/healthz` и `/readyz` исключены. При нулевом трафике отношения и перцентили могут не иметь значения, поэтому перед демонстрацией создаётся нагрузка.

### Детализация рантайма

- CPU: `rate(process_cpu_seconds_total[…])` — потребление CPU процесса в ядрах.
- RSS: `process_resident_memory_bytes` — резидентная память процесса.
- Goroutines: `go_goroutines` — число горутин.
- Heap: `go_memstats_heap_alloc_bytes` — выделенная память Go heap.
- Средняя пауза GC: `rate(go_gc_duration_seconds_sum[…]) / rate(go_gc_duration_seconds_count[…])` — средняя длительность учитываемых GC-пауз за окно; до событий GC значение может отсутствовать.
- Длительность сценария пробера: `repairdesk_probe_duration_seconds` — время последней проверки всей HTTP-цепочки.

При двух репликах runtime-ряды отображаются отдельно по подам; их не следует автоматически считать суммой по всему приложению.

### Почему выбраны эти панели

**RED:** RPS соответствует Rate, доля 5xx — Errors, p95 и длительность пробера — Duration. Это позволяет увидеть, есть ли трафик, возникают ли ошибки и растут ли задержки.

**Golden Signals:** отражены traffic, errors и latency. CPU/память и состояние Go помогают расследовать ресурсные причины, но не являются полноценным измерением saturation: отдельных панелей очередей, ожидания пула БД или CPU throttling в текущем дашборде нет.

**USE:** CPU, RSS и heap дают часть картины использования ресурсов (Utilization). Полное покрытие Saturation и Errors для каждого ресурса не заявляется. Рост goroutines — диагностический сигнал, а не прямое доказательство насыщения.

## 4. Отдельная панель SLA пробера

Пробер каждые 10 секунд последовательно запрашивает категории, оборудование и список заявок через frontend. Успех означает HTTP 200 на всех трёх запросах в пределах общего timeout. Пробер не запускает JavaScript интерфейса и не проверяет визуальное отображение страницы.

Панель **«SLA пробера: хорошие минуты за 30 дней»** использует запрос:

```promql
min(avg_over_time(min_over_time(repairdesk_probe_success{namespace="repair-desk",app="prober"}[1m])[30d:1m]))
```

Хорошая минута — минута, в которой все имеющиеся samples успешны. `min` снаружи выбирает худшую оценку среди имеющихся рядов пробера. Значение выводится в процентах; порог SLA — 99%, внутренний SLO — 99.5%.

Рядом находится панель **«Покрытие истории пробера за 30 дней»**:

```promql
min(count_over_time(min_over_time(repairdesk_probe_success{namespace="repair-desk",app="prober"}[1m])[30d:1m])) / 43200
```

## 5. Импортированный PostgreSQL-дашборд

Используется **Postgres Overview**, [шаблон Grafana №455](https://grafana.com/grafana/dashboards/455-postgres-overview/). Подготовленный JSON: [`postgres.json`](../k8s/monitoring/grafana/postgres.json), datasource заменён на `victoriametrics`. Основной UID — `postgres-exporter-overview`.

Способ загрузки: [заполнить: provisioning / дополнительный импорт через Dashboards → New → Import]. При демонстрационном импорте копии использованы имя `Postgres Overview — demo` и UID `postgres-exporter-demo`.

Выбранные datasource, job, instance и database: [заполнить].

Дашборд содержит:

- **QPS:** частота commits + rollbacks — это транзакции в секунду, не точное число SQL-запросов.
- **Rows:** скорость чтения/возврата/вставки/обновления/удаления строк.
- **Cache hit ratio:** доля попаданий в буферный кеш по статистике PostgreSQL.
- **Number of active connections:** `pg_stat_database_numbackends`, число подключённых backend-процессов; название панели не означает, что все они прямо сейчас выполняют запрос.
- **Conflicts/Deadlocks:** конфликты и взаимоблокировки; нулевые значения являются нормальным результатом.
- **Buffers:** статистика буферов; некоторые старые серии шаблона могут отсутствовать с PostgreSQL 17 и текущим exporter.

`pg_up=1` проверяется в Explore; отдельной панели `pg_up` в исходном шаблоне нет.
