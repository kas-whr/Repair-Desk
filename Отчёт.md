# Отчёт: Repair Desk — система управления заявками на ремонт

## 1. Доменная область

Учёт заявок на ремонт оборудования и устранение технических неисправностей в организации.

Сотрудник сообщает о неисправности (ноутбук, принтер, сеть и т.п.) — создаётся заявка. Заявка относится к категории неисправности, может быть привязана к конкретному оборудованию, получает приоритет и срок выполнения, проходит через статусы от создания до закрытия. По заявке ведётся обсуждение в комментариях.

Бизнес-правила:

1. **Срок выполнения (SLA).** У каждой категории задано нормативное время `sla_hours`. При создании заявки `due_at = created_at + sla_hours`. Приоритет на срок не влияет.
2. **Переходы статусов** ограничены (схема — [docs/status.png](docs/status.png)):

   | Из | В |
   |---|---|
   | `NEW` | `IN_PROGRESS`, `CLOSED` (отмена) |
   | `IN_PROGRESS` | `RESOLVED` |
   | `RESOLVED` | `IN_PROGRESS` (переоткрытие), `CLOSED` |
   | `CLOSED` | — |

   Заявка всегда создаётся в статусе `NEW`. Недопустимый переход → `409 Conflict`.
3. **Списанное оборудование.** Нельзя создать заявку на оборудование со статусом `RETIRED` (или привязать его к заявке) → `400 Bad Request`.
4. **Просроченные заявки.** Заявка просрочена, если `due_at < now` и статус не `RESOLVED` и не `CLOSED`. Признак `overdue` вычисляется при каждом чтении; список можно отфильтровать по нему.
5. **Удаление заявки** разрешено только в статусе `NEW`, иначе → `409 Conflict`.
6. **Закрытая заявка неизменяема**: нельзя редактировать поля, менять статус, добавлять/изменять/удалять комментарии → `409 Conflict`. Заявку в `RESOLVED` редактировать можно.
7. **Категория заявки** задаётся при создании и не меняется.
8. **Удаление справочников:** при удалении категории удаляются её заявки; при удалении оборудования у заявок обнуляется `equipment_id`.

Правила, зависящие от текущего статуса, проверяются атомарно в SQL (`UPDATE … WHERE id = $1 AND status = $expected`), поэтому параллельные запросы не могут их обойти.

## 2. Стек

| Слой | Технологии |
|---|---|
| Backend | Go 1.24, стандартный `net/http` (роутинг, HTTP/1.1), `log/slog` (JSON-логи), драйвер `jackc/pgx/v5` 5.7.5, `google/uuid` |
| База данных | PostgreSQL 17 (`postgres:17-alpine`) |
| Миграции | golang-migrate v4.19.1 (`migrate/migrate:v4.19.1`), SQL-файлы в `migrations/` |
| Frontend | React 19, TypeScript 6, Vite 8, react-router-dom 7; раздаётся nginx 1.27 (`nginx:1.27-alpine`) |
| Инфраструктура | Docker, Docker Compose, GNU Make |

Взаимодействие frontend → backend — REST/JSON по HTTP/1.1. nginx отдаёт статику SPA и проксирует `/api/*` на backend, поэтому браузер работает с одним origin (CORS не нужен). Спецификация API — [docs/api-docs.md](docs/api-docs.md).

Структура backend:

```
cmd/api/main.go              точка входа: конфиг, пул БД, HTTP-сервер, graceful shutdown
internal/config              чтение конфигурации из переменных окружения
internal/domain              сущности, валидация, машина состояний статусов, бизнес-ошибки
internal/service             бизнес-правила
internal/repository/postgres SQL-запросы (pgx)
internal/httpapi             маршруты, обработчики, единый формат ошибок, middleware
```

Сервисы Docker Compose: `postgres` → `migrate` (разовый процесс) → `api` → `frontend`. Порядок запуска обеспечивают `depends_on` с условиями `service_healthy` / `service_completed_successfully`. Запуск всего проекта — `make up`.

## 3. Сущности

ER-диаграмма — [docs/DB-ERdiagram.png](docs/DB-ERdiagram.png). Для всех сущностей реализован CRUD через REST API.

### Category — категория неисправности

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `name` | VARCHAR(100) | NOT NULL, UNIQUE |
| `sla_hours` | INT | NOT NULL, 1…8760 |
| `created_at` | TIMESTAMPTZ | NOT NULL |

Начальные данные (миграция): Hardware — 24 ч, Software — 48 ч, Network — 4 ч, Printer — 12 ч, Other — 72 ч.

### Equipment — оборудование

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `name` | VARCHAR(255) | NOT NULL |
| `inventory_number` | VARCHAR(100) | NOT NULL, UNIQUE |
| `location` | VARCHAR(255) | NOT NULL |
| `status` | VARCHAR(20) | `ACTIVE` / `BROKEN` / `RETIRED`, по умолчанию `ACTIVE` |

### Ticket — заявка

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `title` | VARCHAR(255) | NOT NULL |
| `description` | TEXT | NOT NULL (может быть пустой строкой) |
| `status` | VARCHAR(20) | `NEW` / `IN_PROGRESS` / `RESOLVED` / `CLOSED` |
| `priority` | VARCHAR(20) | `LOW` / `MEDIUM` / `HIGH` / `CRITICAL`, по умолчанию `MEDIUM` |
| `category_id` | UUID | NOT NULL, FK → categories, `ON DELETE CASCADE` |
| `equipment_id` | UUID | NULL, FK → equipment, `ON DELETE SET NULL` |
| `due_at` | TIMESTAMPTZ | NOT NULL, вычисляется при создании |
| `created_at`, `updated_at` | TIMESTAMPTZ | NOT NULL |

### Comment — комментарий к заявке

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `ticket_id` | UUID | NOT NULL, FK → tickets, `ON DELETE CASCADE` |
| `content` | TEXT | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |

Связи: Category 1 — N Ticket, Equipment 1 — N Ticket (необязательная), Ticket 1 — N Comment.

## 4. Соответствие методологии 12 факторов

### I. Кодовая база (Codebase)
**Соответствует.** Одна кодовая база в Git (`github.com/kas-whr/Repair-Desk`), из неё разворачиваются все экземпляры. Монорепозиторий содержит компоненты одного приложения (backend, frontend, миграции); каждый компонент собирается своим Dockerfile, версии компонентов не расходятся.

### II. Зависимости (Dependencies)
**Соответствует.** Все зависимости объявлены явно и зафиксированы:
- Go — `go.mod` + `go.sum` (контрольные суммы);
- frontend — `package.json` + `package-lock.json`, в образе ставятся через `npm ci`;
- базовые образы и инструменты — с указанием версий (`golang:1.24-alpine`, `node:22-alpine`, `nginx:1.27-alpine`, `postgres:17-alpine`, `migrate/migrate:v4.19.1`).

Сборка идёт внутри Docker и не зависит от того, что установлено на машине разработчика. Backend собирается в статический бинарник (`CGO_ENABLED=0`).

Ограничения: теги образов фиксируют версию, но не digest; healthcheck API использует `wget` из базового образа `alpine`.

### III. Конфигурация (Config)
**Соответствует.** Вся конфигурация, которая отличается между окружениями, передаётся через переменные окружения: `POSTGRES_HOST/PORT/DB/USER/PASSWORD/SSLMODE`, `HTTP_PORT`, `LOG_LEVEL`, `FRONTEND_PORT`, `API_UPSTREAM` (адрес backend для nginx — подставляется в шаблон конфигурации при старте контейнера). Код читает только окружение (`internal/config`), значений по умолчанию для учётных данных нет: при их отсутствии процесс сразу завершается с ошибкой. Файл `.env` в репозиторий не коммитится, в репозитории лежит шаблон `.env.example`.

Ограничение: `sslmode=disable` для контейнера миграций задан в `docker-compose.yml`, а не переменной.

### IV. Сторонние службы (Backing services)
**Соответствует.** PostgreSQL — подключаемый ресурс: приложение получает только адрес и учётные данные из окружения. Чтобы заменить локальную БД на управляемую (облачную), достаточно поменять переменные, код не меняется. Локальный запуск (`make run-api`) и запуск в Docker используют один и тот же код, отличается только `POSTGRES_HOST`.

### V. Сборка, релиз, выполнение (Build, release, run)
**Соответствует частично.**
- Сборка: multi-stage Dockerfile собирает неизменяемые образы (`repair-desk-api`, `repair-desk-frontend`).
- Релиз: образ + конфигурация из окружения, объединяются при запуске контейнера.
- Выполнение: `docker compose up` запускает готовые образы, код в рантайме не меняется.

Чего нет: образы помечаются тегом `latest` без номера версии, нет реестра образов и CI-пайплайна, поэтому нельзя откатиться к конкретному релизу по идентификатору. Это задача следующего этапа (вместе с Kubernetes).

### VI. Процессы (Processes)
**Соответствует.** Backend — stateless: нет сессий, кэша в памяти и файлов на локальном диске; всё состояние хранится в PostgreSQL. Любой запрос может обработать любой экземпляр. Состояние интерфейса (фильтры, пагинация) хранится в браузере (в URL).

### VII. Привязка портов (Port binding)
**Соответствует.** Backend сам поднимает HTTP-сервер (`net/http`) на порту из `HTTP_PORT` и не требует внешнего веб-сервера или контейнера приложений. Frontend-образ содержит nginx и отдаёт сервис на порту 80. Наружу порты публикуются через `ports` в Compose (`HTTP_PORT`, `FRONTEND_PORT`).

### VIII. Параллелизм (Concurrency)
**Соответствует по архитектуре, масштабирование не настроено.** Так как процесс stateless (фактор VI), backend масштабируется горизонтально запуском дополнительных экземпляров. Внутри процесса каждый запрос обслуживается отдельной горутиной, к БД — пул соединений `pgxpool`. Корректность при параллельной работе нескольких экземпляров обеспечивают атомарные условные UPDATE/DELETE в SQL.

Ограничение: в `docker-compose.yml` у `api` зафиксирован публикуемый порт хоста, поэтому `docker compose up --scale api=N` не сработает без балансировщика. Горизонтальное масштабирование планируется в Kubernetes.

### IX. Утилизируемость (Disposability)
**Соответствует.**
- Быстрый запуск: один статический бинарник; при старте только чтение конфигурации и проверка соединения с БД (таймаут 10 с). Если БД недоступна, процесс завершается с ошибкой, а Docker перезапускает его (`restart: unless-stopped`).
- Корректное завершение: по `SIGTERM`/`SIGINT` сервер перестаёт принимать новые соединения, дожидается завершения текущих запросов (до 10 с) через `http.Server.Shutdown` и закрывает пул соединений с БД.
- Каждое изменение данных выполняется одним SQL-запросом, поэтому остановка процесса не оставляет данные в промежуточном состоянии.

### X. Паритет окружений (Dev/prod parity)
**Соответствует в рамках имеющихся окружений.** Локально используются те же Docker-образы и та же версия PostgreSQL (17), что и при развёртывании; Compose поднимает полный стек одной командой. Миграции схемы одинаково применяются в любом окружении. Для разработки дополнительно есть `make run-api` / `make run-frontend`, но они подключаются к той же PostgreSQL в Docker, а не к другой СУБД.

Ограничение: отдельного production-окружения пока нет, поэтому паритет проверен только между локальным запуском и Docker.

### XI. Журналирование (Logs)
**Соответствует.** Приложение не управляет файлами логов: backend пишет структурированные JSON-логи (`log/slog`) в stdout — по одной строке на HTTP-запрос (`request_id`, метод, путь, статус, длительность), а также ошибки и паники со stack trace. Уровень задаётся `LOG_LEVEL`. nginx и PostgreSQL в официальных образах тоже пишут в stdout/stderr. Сбор и просмотр — средствами окружения (`docker compose logs`, `make logs`). Заголовок `X-Request-ID` возвращается клиенту, по нему можно найти запрос в логах.

### XII. Административные процессы (Admin processes)
**Соответствует.** Миграции БД — разовый процесс в отдельном контейнере `migrate`: он запускается в том же окружении и с той же конфигурацией, выполняется и завершается. Файлы миграций хранятся в том же репозитории, что и код. При `make up` миграции применяются автоматически, а backend стартует только после их успешного завершения. Ручные команды: `make migrate-up`, `make migrate-down n=1`, `make migrate-create name=…`.
