# Отчёт: метрики Repair Desk в VictoriaMetrics

## Содержимое архива

| Путь | Что внутри |
|---|---|
| `source/` | Исходный код приложения (Go backend, React frontend, миграции, Dockerfile'ы) |
| `source/internal/metrics/metrics.go` | Определение всех метрик приложения |
| `manifests/*.yaml` | Манифесты приложения (namespace, postgres + postgres-exporter, migrate, api, frontend) |

## Стек

| Компонент | Технология |
|---|---|
| Приложение | Go 1.24 (`net/http`), PostgreSQL 17, React + nginx; Kubernetes (minikube) |
| TSDB | VictoriaMetrics single v1.154.0, Helm-чарт `vm/victoria-metrics-single` 0.49.0, namespace `monitoring` |
| Сбор метрик | Pull-модель: встроенный в VictoriaMetrics single скрейпер (`-promscrape.config`), service discovery `kubernetes_sd_configs` по аннотациям `prometheus.io/*` |
| Метрики приложения | `github.com/prometheus/client_golang` v1.23.2, формат Prometheus text / OpenMetrics |
| Метрики PostgreSQL | `postgres-exporter` v0.20.1 (sidecar в поде Postgres) |

Установка (по инструкции docs.victoriametrics.com/guides/k8s-monitoring-via-vm-single/, шаги 1–2):

```sh
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm repo update
helm install vm-single vm/victoria-metrics-single --version 0.49.0 \
  -n monitoring --create-namespace -f manifests/monitoring/vmsingle-values.yaml
kubectl apply -f manifests/
```

## Экспортеры

### 1. Метрики рантайма Go — встраиваемая библиотека

Библиотека `client_golang` регистрирует стандартные коллекторы:
- `go_*` — рантайм Go: горутины (`go_goroutines`), память кучи (`go_memstats_*`), сборщик мусора (`go_gc_duration_seconds`), потоки;
- `process_*` — процесс: CPU (`process_cpu_seconds_total`), резидентная память (`process_resident_memory_bytes`), открытые файлы.

### 2. Технические и бизнес-метрики — собственная реализация

Метрики объявлены в `internal/metrics/metrics.go` и обновляются в сервисном слое и HTTP-слое.

**Endpoint.** API отдаёт метрики на **отдельном порту `9090`**, путь `/metrics` (переменная `METRICS_PORT`). Основной порт `8080` и frontend этот путь не проксируют, поэтому метрики доступны только изнутри кластера, без авторизации — как требует pull-модель. При запросе с `Accept: application/openmetrics-text` ответ отдаётся в формате OpenMetrics.

### 3. Метрики PostgreSQL — готовый внешний экспортер

`postgres-exporter` запущен вторым контейнером в поде `postgres-0` (StatefulSet). Контейнеры пода делят сетевое пространство, поэтому экспортер подключается к БД по `localhost:5432`; учётные данные берёт из того же Secret `postgres-credentials`. Метрики — на порту `9187`: `pg_up`, `pg_stat_database_*` (подключения, транзакции, чтения/записи по БД), `pg_settings_*`, `pg_locks_count` и др.

## Бизнес-метрики

| Метрика | Тип | Лейблы | Когда меняется | Что показывает |
|---|---|---|---|---|
| `repairdesk_tickets_created_total` | counter | `category`, `priority` | заявка создана | Поток заявок: сколько и каких неисправностей сообщают, по категориям и приоритетам |
| `repairdesk_ticket_status_changes_total` | counter | `from`, `to` | успешная смена статуса | Движение заявок по жизненному циклу: взято в работу, решено, переоткрыто, отменено, закрыто |
| `repairdesk_tickets_resolved_total` | counter | `within_sla` = `true` / `false` | заявка переведена в `RESOLVED` | Соблюдение SLA: решена ли заявка до `due_at` (срок по нормативу категории) |
| `repairdesk_ticket_resolution_seconds` | histogram | — | заявка переведена в `RESOLVED` | Время решения заявки от создания; бакеты от 1 минуты до недели |
| `repairdesk_business_rule_violations_total` | counter | `rule` | запрос отклонён бизнес-правилом | Сколько раз срабатывают правила: `INVALID_STATUS_TRANSITION`, `TICKET_CLOSED`, `TICKET_NOT_DELETABLE`, `EQUIPMENT_RETIRED`, `ALREADY_EXISTS` |

Дополнительно техническая метрика `repairdesk_http_request_duration_seconds` (histogram, лейблы `method`, `route`, `status`) — число и длительность HTTP-запросов по маршрутам. `route` — шаблон маршрута (`GET /api/v1/tickets/{id}`) без ID, чтобы число временных рядов было ограничено.

Ряды `tickets_resolved_total` и `business_rule_violations_total` для всех известных значений лейблов создаются со значением 0 при старте, поэтому `rate()` и `increase()` работают сразу, до первого события.

Счётчики ведутся в каждой реплике API отдельно; в запросах суммируются через `sum`.

Примеры запросов (PromQL / MetricsQL):

```promql
# Заявок создано за час по категориям
sum by (category) (increase(repairdesk_tickets_created_total[1h]))

# Доля заявок, решённых в срок SLA
sum(rate(repairdesk_tickets_resolved_total{within_sla="true"}[1h]))
  / sum(rate(repairdesk_tickets_resolved_total[1h]))

# 90-й перцентиль времени решения заявки
histogram_quantile(0.9, sum by (le) (rate(repairdesk_ticket_resolution_seconds_bucket[1d])))

# Нарушения бизнес-правил в минуту
sum by (rule) (rate(repairdesk_business_rule_violations_total[5m])) * 60
```

## Service discovery

Поды, с которых нужно собирать метрики, помечены аннотациями в шаблоне пода:

| Под | `prometheus.io/scrape` | `prometheus.io/port` | `prometheus.io/path` |
|---|---|---|---|
| `api` (Deployment, 2 реплики) | `"true"` | `"9090"` | `/metrics` |
| `postgres-0` (StatefulSet) | `"true"` | `"9187"` | `/metrics` |

В values Helm-чарта к конфигурации из инструкции (victoriametrics, apiservers, nodes, cadvisor) добавлен job `kubernetes-pods` с `kubernetes_sd_configs: role: pod`:
- `keep` по `prometheus.io/scrape: "true"`;
- `keep_if_equal` номера порта контейнера и `prometheus.io/port`: под с несколькими портами (postgres 5432 + exporter 9187) порождает таргет на каждый порт, остаётся только порт метрик;
- `drop` завершённых подов (`Succeeded`/`Failed`, например Job `migrate`);
- путь из `prometheus.io/path`, лейблы `namespace`, `pod`, `container` и все лейблы пода.

Новые реплики (`kubectl scale`) подхватываются автоматически, без изменения конфигурации.

Права на чтение подов, нод и endpoints через API Kubernetes (ServiceAccount + ClusterRole) создаёт Helm-чарт.

> В инструкции VictoriaMetrics single сам выполняет сбор метрик (`server.scrape.enabled: true`), отдельный vmagent не устанавливается. Поэтому статус скрейпинга проверяется на самом VictoriaMetrics: `http://localhost:8428/targets` (вместо `:8429` у vmagent).
