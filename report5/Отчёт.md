# Отчёт: SLI, SLO и SLA для Repair Desk

Метрики собираются VictoriaMetrics single (minikube, namespace `monitoring`) с подов, помеченных аннотациями `prometheus.io/*` (ДЗ по метрикам). Графики строятся в vmui: `kubectl -n monitoring port-forward svc/vm-single-victoria-metrics-single-server 8428:8428` → http://localhost:8428/vmui/.

## 1. Выбранные метрики

| Метрика | Тип | Источник | Для какого SLI |
|---|---|---|---|
| `repairdesk_http_request_duration_seconds_count{method, route, status}` | counter (часть histogram) | API, ДЗ по метрикам | SLI-1 доступность |
| `repairdesk_http_request_duration_seconds_bucket{le, method, route, status}` | histogram | API, ДЗ по метрикам | SLI-2 задержка |
| `repairdesk_probe_success` | gauge 0/1 | **пробер** (новый) | SLI-3 доступность глазами пользователя |
| `repairdesk_probe_duration_seconds` | gauge | пробер | вспомогательная: длительность сценария |
| `repairdesk_probe_runs_total{result}` | counter | пробер | вспомогательная: число прогонов |

**`repairdesk_http_request_duration_seconds`** — каждая обработка HTTP-запроса API: `route` — шаблон маршрута (`GET /api/v1/tickets/{id}`), `status` — код ответа, бакеты по длительности (5 мс … 10 с). `_count` — число запросов, `_bucket{le="0.25"}` — число запросов не дольше 250 мс.

**Пробер** (`cmd/prober`, Deployment `prober`) — синтетический пользователь. Каждые 10 секунд выполняет сценарий «открыть страницу заявок» — те же запросы, что делает браузер: `GET /api/v1/categories`, `GET /api/v1/equipment`, `GET /api/v1/tickets?limit=20` — через Service `frontend`, то есть через всю цепочку nginx → api → PostgreSQL. Прогон успешен, если все ответы `200` и сценарий уложился в 2 секунды; результат пишется в `repairdesk_probe_success`.

Из SLI исключены `GET /healthz` и `GET /readyz` — это пробы Kubernetes, а не запросы пользователей.

## 2. SLI, SLO и SLA

Обозначения: `W` — окно оценки. Для SLO и SLA `W` = 30 дней; на графиках для демонстрации используются короткие окна (1–30 минут), чтобы изменения было видно сразу.

### SLI-1. Доступность API (Request Based)

**SLI** — доля запросов к API, обработанных без ошибки сервера (не 5xx):

```
SLI₁ = good / all = Σ запросов со status ≠ 5xx / Σ всех запросов   (за окно W)
```

```promql
sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)", status!~"5.."}[W]))
/
sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)"}[W]))
```

Ответы 4xx (нарушение бизнес-правил, 404) считаются успешными: сервис отработал корректно, ошибка на стороне клиента.

**SLO-1:** SLI₁ ≥ **99.5 %** за 30 дней. Бюджет ошибок — 0.5 % запросов.

### SLI-2. Задержка API (Request Based)

**SLI** — доля запросов, обработанных не дольше 250 мс:

```
SLI₂ = Σ запросов с duration ≤ 250 мс / Σ всех запросов   (за окно W)
```

```promql
sum(increase(repairdesk_http_request_duration_seconds_bucket{route!~"GET /(healthz|readyz)", le="0.25"}[W]))
/
sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)"}[W]))
```

**SLO-2:** SLI₂ ≥ **99 %** за 30 дней. В нормальном режиме медиана ~1 мс, p95 — десятки миллисекунд, поэтому 250 мс оставляют запас и при этом ловят реальную деградацию.

### SLI-3. Доступность сервиса глазами пользователя (Time Based, пробер)

**SLI** — доля «хороших» минут. Минута хорошая, если **все** прогоны пробера за эту минуту успешны:

```
good_minute(t) = min(probe_success за минуту t)          ∈ {0, 1}
SLI₃ = Σ good_minute / число минут в окне W
```

```promql
avg_over_time( min_over_time(repairdesk_probe_success[1m])[W:1m] )
```

**SLO-3:** SLI₃ ≥ **99.5 %** за 30 дней. Бюджет ошибок — 0.5 % × 43 200 мин ≈ **216 минут** простоя в месяц.

Почему нужен пробер, если есть SLI-1: метрики API собирает сам API. Если API полностью недоступен (все поды упали, nginx отвечает 502), упавшие поды не считают запросы — SLI₁ остаётся 100 %, хотя пользователи видят ошибку. Пробер проверяет сервис снаружи, как пользователь, и ловит такие отказы (см. сценарий 3 в разделе 4).

### Бюджет ошибок и скорость его расходования

```
Остаток бюджета  = 1 − (1 − SLI_W) / (1 − SLO)        1 — бюджет не тронут, 0 — исчерпан
Burn rate        = (1 − SLI_короткое_окно) / (1 − SLO)  1 — бюджет расходуется ровно к концу окна
```

```promql
# Остаток бюджета SLO-1 (на графике ограничен снизу нулём)
clamp_min(1 - (1 - (
  sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)", status!~"5.."}[W]))
  / sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)"}[W]))
)) / (1 - 0.995), 0)
```

### SLA

SLA — внешнее обязательство перед пользователями системы (сотрудниками организации). Оно мягче внутренних SLO: SLO — цель команды, а SLA — порог, при нарушении которого наступают последствия. Запас между ними даёт время отреагировать до нарушения SLA.

| | Показатель | SLO (внутренняя цель) | **SLA (обязательство)** |
|---|---|---|---|
| Доступность | SLI-3, хорошие минуты по проберу | 99.5 % | **99.0 %** в календарный месяц (≤ 432 мин простоя) |
| Скорость | SLI-2, запросы ≤ 250 мс | 99 % | **95 %** в календарный месяц |

**Общий SLA:** месяц считается выполненным, если выполнены оба пункта:

```
SLA_выполнен = (SLI₃_месяц ≥ 0.99) ∧ (SLI₂_месяц ≥ 0.95)
```

При нарушении: разбор инцидента (postmortem) в течение 5 рабочих дней и приоритет работ по надёжности над новой функциональностью в следующем месяце.

Для SLA выбран SLI-3, а не SLI-1: пробер измеряет то, что видит пользователь, через всю цепочку frontend → API → БД, включая полный отказ API.

## 3. Графики в vmui

Каждый блок кода ниже — **отдельный запрос в отдельном поле**. Первый запрос вводится в поле Query, остальные добавляются кнопкой **Add Query** (появляется новое поле), после чего **Execute** рисует все запросы на одном графике. Горизонтальные линии SLO/SLA — константы `vector(…)`. Для демонстрации окно `W` = 2m (SLI «сейчас»; при малой нагрузке окно 1m даёт слишком шумную линию); период графика — Last 30 minutes.

### График 1 — SLI-1 доступность API

Запрос 1 — SLI:
```promql
sum(rate(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)", status!~"5.."}[2m])) / sum(rate(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)"}[2m]))
```

Запрос 2 — SLO 99.5 %:
```promql
vector(0.995)
```

### График 2 — SLI-2 задержка API

Запрос 1 — SLI:
```promql
sum(rate(repairdesk_http_request_duration_seconds_bucket{route!~"GET /(healthz|readyz)", le="0.25"}[2m])) / sum(rate(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)"}[2m]))
```

Запрос 2 — SLO 99 %:
```promql
vector(0.99)
```

Запрос 3 — SLA 95 %:
```promql
vector(0.95)
```

### График 3 — SLI-3 пробер (хорошие минуты за последние 10 минут)

Запрос 1 — SLI:
```promql
avg_over_time(min_over_time(repairdesk_probe_success[1m])[10m:1m])
```

Запрос 2 — SLO 99.5 %:
```promql
vector(0.995)
```

Запрос 3 — SLA 99 %:
```promql
vector(0.99)
```

### График 4 — остаток бюджета ошибок SLO-1 за 30 минут

Один запрос:
```promql
clamp_min(1 - (1 - (sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)", status!~"5.."}[30m])) / sum(increase(repairdesk_http_request_duration_seconds_count{route!~"GET /(healthz|readyz)"}[30m])))) / (1 - 0.995), 0)
```

Вспомогательные (каждый — отдельным запросом): `repairdesk_probe_success`, `repairdesk_probe_duration_seconds`.

## 4. Изменения приложения для скринкаста

Чтобы показать изменение SLI, в приложение добавлено:

1. **Пробер** — `cmd/prober/main.go`, манифест `k8s/50-prober.yaml`. Тот же образ, что у API, другой бинарник. Даёт фоновый поток запросов и метрику `repairdesk_probe_success`.
2. **Управляемая поломка API (fault injection)** — `internal/httpapi/fault.go`. Включается переменными окружения, по умолчанию выключена; действует только на `/api/*` (пробы Kubernetes не затрагиваются):
   - `FAULT_ERROR_RATE` (0…1) — доля запросов, на которые API отвечает `500 INJECTED_FAULT`;
   - `FAULT_DELAY_MS` — задержка каждого запроса.

Сценарии (проверены; изменения на графиках видны через 1–2 минуты):

| # | Команда | Что происходит | SLI-1 | SLI-2 | SLI-3 (пробер) |
|---|---|---|---|---|---|
| 0 | — | Норма | 1.00 | 1.00 | 1.00 |
| 1 | `kubectl -n repair-desk set env deployment/api FAULT_ERROR_RATE=0.3` | 30 % ответов API — 500 | ↓ ~0.7 | 1.00 | ↓ почти каждый прогон падает (3 запроса: 0.7³ ≈ 34 % успеха), хорошие минуты → 0 |
| 2 | `kubectl -n repair-desk set env deployment/api FAULT_ERROR_RATE- FAULT_DELAY_MS=400` | Ошибок нет, каждый запрос +400 мс | восстанавливается | ↓ ~0 | прогоны успешны, но сценарий длится 1.2 с вместо ~0.01 с (`repairdesk_probe_duration_seconds`) |
| 3 | `kubectl -n repair-desk set env deployment/api FAULT_DELAY_MS-` и `kubectl -n repair-desk scale deployment api --replicas=0` | API полностью недоступен, nginx → 502 | **остаётся 1.00** — API ничего не считает | — | ↓ 0: пробер видит отказ |
| 4 | `kubectl -n repair-desk scale deployment api --replicas=2` | Восстановление | 1.00 | 1.00 | растёт по мере выхода плохих минут из окна |

`kubectl set env` перезапускает поды API (rolling update); счётчики начинаются с нуля, `rate()`/`increase()` корректно обрабатывают сброс.

Фактические значения при проверке (окно 2m):

| Шаг | SLI-1 | SLI-2 | Хорошие минуты пробера (5m) | Последний прогон пробера |
|---|---|---|---|---|
| Норма | 1.0000 | 1.0000 | 1.0000 | 1, ~0.01 с |
| 30 % ошибок | 0.8944 и падает | 1.0000 | 0.6667 | 0 (`GET /api/v1/categories: status 500`) |
| Задержка 400 мс | 0.8710 (хвост ошибок в окне) | 0.3978 | 0.4000 | 1, 1.21 с |
| API = 0 реплик | **1.0000** | — | 0.4000 | 0 (`status 502`) |
| Восстановление | 1.0000 | 1.0000 | 0.2000 → растёт | 1 |
