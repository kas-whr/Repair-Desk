# Логирование Repair Desk в VictoriaLogs

Приложение Repair Desk (namespace `repair-desk` в minikube) пишет логи в формате JSON в stdout. Vector, запущенный как DaemonSet, собирает их с ноды и отправляет в VictoriaLogs. Поверх логов работает vmalert с алертом на ошибки.

## Содержимое архива

| Файл | Что внутри |
|---|---|
| `manifests/00-namespace.yaml` | Namespace `logging` |
| `manifests/10-victorialogs.yaml` | VictoriaLogs v1.53.0 single-node: StatefulSet + PVC 2 Gi + Service `victorialogs:9428`, хранение 7 дней |
| `manifests/20-vector.yaml` | Шиппер Vector 0.59.0: DaemonSet, RBAC, **конфиг Vector** (ConfigMap `vector-config`, ключ `vector.yaml`) |
| `manifests/30-vmalert.yaml` | Бонус: vmalert v1.154.0 + правило алерта (ConfigMap `vmalert-rules`) |
| `screenshots/` | Скриншоты vmui и vmalert |

Деплой — обычными манифестами, без Helm:

```sh
kubectl apply -f manifests/
kubectl -n logging port-forward svc/victorialogs 9428:9428   # vmui: http://localhost:9428/select/vmui/
kubectl -n logging port-forward svc/vmalert 8880:8880        # vmalert: http://localhost:8880/vmalert/alerts
```

> В VictoriaLogs v1.53 vmui открывается по `/select/vmui/` (путь `/vmui/` возвращает 400).

Формат записи приложения (API):

```json
{"timestamp":"2026-10-15T21:38:08.079Z","level":"warn","message":"http request","service.name":"repair-desk-api",
 "request_id":"bd7acebb4a93a38db66b724d5520a934","method":"POST","route":"POST /api/v1/equipment",
 "path":"/api/v1/equipment","status":409,"duration_ms":24.875}
```

nginx (frontend) пишет access-лог в той же схеме; PostgreSQL пишет текст, уровень из него извлекает Vector. К каждой записи Vector добавляет `k8s.namespace`, `k8s.pod`, `k8s.container`, `k8s.node`.

## LogsQL-запросы

### (а) Сырые записи за последние 15 минут

```logsql
_time:15m
```

Все записи всех сервисов приложения за 15 минут, от новых к старым, со всеми полями. Используется как отправная точка: посмотреть, что вообще происходит, и какие поля есть у записей.

![(а) Сырые записи за 15 минут](screenshots/a-raw.png)

### (б) Фильтр по полю: ошибки

```logsql
_time:15m level:error
```

Только записи уровня `error`. В нашем случае это ошибки PostgreSQL `duplicate key value violates unique constraint`: `equipment_inventory_number_key` — попытка создать оборудование с уже существующим инвентарным номером, `categories_name_key` — категорию с уже существующим именем (API в обоих случаях отвечает 409). Это первый запрос, который нужен при разборе инцидента; на нём же построен алерт (см. «Бонус»).

![(б) Записи уровня error](screenshots/b-errors.png)

### (в) stats с группировкой: количество записей по сервису и уровню

```logsql
_time:15m | stats by (service.name, level) count() as logs
```

Сколько записей каждого уровня пишет каждый сервис. Показывает общую картину здоровья: доля `warn`/`error` относительно `info`. Число `warn` у `repair-desk-frontend` совпадает с `repair-desk-api`: это одни и те же запросы — nginx видит тот же статус 4xx, что вернул API. Записи `postgres` без уровня — строки-продолжения многострочных ошибок PostgreSQL (`DETAIL:`, `STATEMENT:`).

![(в) Количество записей по service.name и level](screenshots/c-stats.png)

### (г) Агрегирующий запрос: перцентили латентности API по маршрутам

```logsql
_time:15m service.name:"repair-desk-api"
  | stats by (route) count() as requests,
      quantile(0.5, duration_ms) as p50_ms,
      quantile(0.95, duration_ms) as p95_ms
  | sort by (requests desc)
```

Для каждого маршрута API: число запросов, медиана (p50) и 95-й перцентиль (p95) времени обработки в миллисекундах. Группировка по `route` (шаблон вида `GET /api/v1/tickets/{id}`), а не по `path`: в `path` есть UUID, и каждая заявка давала бы отдельную группу. Чтение (`GET`) обрабатывается быстро и стабильно: p50 ~0.6–1.2 мс, p95 до ~2.5 мс. Запись (`POST`, `PATCH`) медленнее: p50 1–2 мс, а p95 доходит до 20–30 мс — это запросы, которые пишут в БД (вставка, проверка уникальности, смена статуса). Для маршрутов с 1–2 запросами p50 и p95 совпадают: перцентиль по такой выборке не показателен.

![(г) p50/p95 латентности по маршрутам](screenshots/d-quantile.png)

## Почему выбран такой способ доставки логов

Выбран **агент Vector в DaemonSet**, который читает файлы логов контейнеров с ноды (`/var/log/pods`), а не сайдкар и не прямая отправка из приложения.

- **Приложение не знает о системе логирования.** Оно только пишет JSON в stdout (12-factor, фактор XI: логи — поток событий, маршрутизацией занимается окружение). В коде нет клиента VictoriaLogs, адреса, ретраев и буферизации; при замене хранилища логов приложение не меняется.
- **Собираются все контейнеры, включая чужие образы.** PostgreSQL и nginx — готовые образы, которые не умеют отправлять логи в VictoriaLogs сами; файловый сбор с ноды работает для любого контейнера.
- **DaemonSet, а не сайдкар.** Один агент на ноду вместо дополнительного контейнера в каждом поде: меньше потребление ресурсов, манифесты приложения не меняются, новые поды подхватываются автоматически.
- **Метаданные Kubernetes.** Источник `kubernetes_logs` сам добавляет к записи имя пода, контейнера, namespace и ноды (через API Kubernetes).
- **Обработка на стороне агента.** На языке VRL Vector разбирает JSON-строки, извлекает уровень из текстовых логов PostgreSQL, отбрасывает пустые строки и пробы Kubernetes (`/healthz`, `/readyz`, `kube-probe`), которые иначе забивали бы логи каждые 5–10 секунд.
- **Надёжность.** Позиции чтения файлов сохраняются на ноде (hostPath), поэтому после перезапуска агента логи не дублируются; при недоступности VictoriaLogs Vector повторяет отправку.
- **Почему Vector.** Лёгкий (один бинарник на Rust, десятки МБ памяти), интеграция с VictoriaLogs описана в официальной документации (`/insert/jsonline`). Fluent Bit подошёл бы так же; Vector выбран из-за более читаемого языка преобразований VRL.

## Бонус: алерт через vmalert

vmalert раз в минуту выполняет LogsQL-запрос к VictoriaLogs. Правило построено на запросе (б):

```yaml
- alert: RepairDeskErrorLogs
  expr: '_time:5m level:error | stats by (service.name) count() as errors | filter errors:>0'
  labels:
    severity: warning
  annotations:
    summary: '{{ index $labels "service.name" }}: {{ $value }} error log(s) in the last 5 minutes'
```

Алерт срабатывает, если за последние 5 минут у какого-либо сервиса есть записи уровня `error`, отдельно для каждого `service.name`. Alertmanager не развёрнут (`-notifier.blackhole`): состояние алертов видно в веб-интерфейсе vmalert. Проверка: создание оборудования с существующим инвентарным номером → ошибка в логах PostgreSQL → в течение минуты алерт `RepairDeskErrorLogs` переходит в `firing` с `service.name=postgres`.
